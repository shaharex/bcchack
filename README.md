# AI Requirements Validator

Проверяет требования в Markdown и PDF с помощью Gemini, сверяет цитаты с источником и формирует отчёт на русском языке.

## Установка и ключ Gemini

Откройте PowerShell в корне проекта. Используйте Python 3.11 или новее.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e .
Copy-Item .env.example .env
```

macOS и Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
cp .env.example .env
```

Создайте ключ в Google AI Studio и запишите его в поле `GEMINI_API_KEY` файла `.env`. CLI читает `.env` из текущего каталога. Переменные процесса имеют приоритет. `GEMINI_MODEL` задаёт модель, `GEMINI_TIMEOUT_MS` — таймаут HTTP-запроса в миллисекундах, `GEMINI_MAX_ATTEMPTS` — число попыток, `GEMINI_MAX_RETRY_WAIT_SECONDS` — общий бюджет ожидания между попытками одного запроса (по умолчанию 60 секунд). `GEMINI_FALLBACK_MODELS` — список резервных моделей через запятую. Если основная модель после всех попыток отвечает HTTP 503, 504 или 429, CLI переключается на следующую модель до конца прогона и указывает обе модели в паспорте. Версия агента в паспорте по умолчанию берётся из `git describe` (тег или коммит, с пометкой `-dirty` при незакоммиченных изменениях). `VALIDATOR_AGENT_VERSION` её переопределяет. [Ключи Gemini API](https://ai.google.dev/gemini-api/docs/api-key)

## Запуск

```powershell
python -m requirements_validator --input path/to/requirements.md
python -m requirements_validator --input path/to/requirements.md --output report.md
python -m requirements_validator --input path/to/requirements.md --format pdf --output review.pdf
python -m requirements_validator --input path/to/requirements.pdf --output review.docx
python -m requirements_validator --input path/to/requirements.md --format html
```

Прогон по выданному документу:

```bash
python -m requirements_validator --input mdfile/requirements.md --output reports/report.md
```

Передайте исходный документ через `--input`. Формат по умолчанию — UTF-8 Markdown. Если указано поддерживаемое расширение в `--output`, CLI определит формат по нему. Флаг `--format` принимает `md`, `pdf`, `docx` и `html`. Без `--output` CLI записывает `report.<формат>` в текущем каталоге. Каталог для отчёта должен существовать. При ошибке команда возвращает ненулевой код и выводит сообщение в stderr.

Для PDF и DOCX установите `python -m pip install -e ".[export]"`. Для PDF также нужен Pango. Команды установки для Windows и инструкция по экспорту готового JSON доступны в [README шаблона](report_template/README.md).

Markdown-отчёт содержит паспорт прогона, карту требований, оценку каждого требования, проверку спецификации, подтверждённые дефекты с цитатами и серьёзностью, вопросы к заказчику, сводку и рекомендации по готовности. Карта указывает отдельно место исходного идентификатора и место формулировки. Идентификаторы `L3-L5` обозначают диапазоны строк Markdown, `P2` — вторую страницу PDF. Смещения в квадратных скобках отсчитываются от начала блока в символах Unicode, начиная с нуля. Правая граница исключается.

Извлечённые элементы получают номера `R-001`, `R-002` в порядке исходных позиций. Для каждого блока сохраняется его роль в проверке. Контракты и факты спецификации, критерии приёмки, составные и атомарные требования различаются в карте. Пропуск блока или строки в анализируемой таблице вызывает повторную проверку извлечения. Отчёт показывает цитаты и исходы подтверждённых конфликтов, а также основания для отклонения кандидатов.

## Критерии качества

Проверка следует ISO/IEC/IEEE 29148:2018 (п. 5.2.5 и 5.2.6) и IEEE Std 830-1998 (п. 4.3). Каждое требование оценивается по свойствам п. 5.2.5: необходимость, уместность уровня детализации, однозначность, полнота, единичность, выполнимость, проверяемость, корректность и соответствие шаблону. Дополнительно проверяется непротиворечивость. Документ в целом оценивается отдельным запросом по свойствам набора из п. 5.2.6 (полнота, согласованность, выполнимость, понятность, возможность валидации) и спецификации из п. 4.3 (корректность, однозначность, полнота, согласованность, ранжированность, проверяемость, модифицируемость, прослеживаемость).

Часть свойств документа измеряется в Python без модели: доля элементов с собственным идентификатором, маркеры приоритета, незаполненные поля шаблона и пустые разделы, дословные повторы и наличие глоссария. Модель получает эти показатели как указатели на блоки, выносит оценку и цитирует источник. Её замечания проходят ту же сверку цитат и независимую проверку, что и остальные. Корректность и необходимость оцениваются только по самому документу. Если подтвердить их может лишь заказчик, ставится «нельзя оценить».

Раздел отчёта «Соответствие стандартам» содержит строку для каждого пункта стандарта со ссылками на подтверждённые замечания и таблицу измеренных показателей. Статус «Не соответствует» ставится только при подтверждённом замечании. Эта же матрица выводится в PDF, DOCX и HTML.

## Исполняемая проверка

Модель переводит поведенческие правила документа (события, состояние, обновления, обязательные результаты и ограничения) в небольшую исполняемую модель. У каждого правила есть точная цитата. Затем модель описывает входные данные примеров приёмки и сгенерированных сценариев: изменение настройки после срабатывания, граница периода, возврат, повтор события. Результат вычисляет Python, а не модель. Выражения выполняются в ограниченной песочнице без `eval`.

Замечание предлагается в трёх случаях: пример приёмки не следует из правил, одно правило требует результата, который запрещает другое, или правилу нужно значение, которого не передаёт ни один документированный источник. Python проверяет перевод статически и возвращает модели точную диагностику для исправления: неизвестные имена, обращение к таблице без ключа, непереведённые пронумерованные требования, недостающие поля времени. Если модель не воспроизводит ни одного из нескольких примеров приёмки, перевод считается ненадёжным и расхождения с примерами не сообщаются. Все предложения проходят ту же сверку цитат и независимую проверку, что и остальные замечания. Результаты сценариев выводятся в разделе «Исполняемая проверка».

Качество перевода зависит от модели. `EXECUTABLE_GEMINI_MODEL` задаёт более сильную модель только для этого шага, основная цепочка служит резервом. `VALIDATOR_EXECUTABLE=0` отключает проверку.

Серьёзность зависит от подтверждённого последствия. Высокая означает, что нельзя надёжно реализовать или проверить существенное поведение. Средняя указывает на необходимое решение ограниченного масштаба. Низкая относится к локальным замечаниям документации. Python присваивает уровень после проверки доказательств. Для настройки задайте `VALIDATOR_SEVERITY_OVERRIDES='{"verifiability":"high"}'` в `.env`. В Python можно переопределить обоснование через `SeverityRule`.

## Ограничения

- Markdown должен быть в UTF-8. PDF должен содержать доступный текстовый слой. При пропуске страницы с изображениями без текстового слоя CLI выводит предупреждение с номером страницы. Выполните OCR перед проверкой отсканированных страниц. Порядок текста в многоколоночных PDF и таблицах зависит от извлечения PyMuPDF. Раздел PDF определяется закладками на уровне страниц.
- Документ и данные анализа передаются в Gemini. Длинные документы ограничены контекстом, объёмом ответа и квотами модели. Индивидуальная проверка группирует до четырёх требований в запросе с полной матрицей критериев для каждого требования. При некорректном структурированном ответе группа делится на меньшие.
- Цитаты сверяются посимвольно с текстом парсера. Полнота извлечения, смысловая связь доказательств и качество вопросов зависят от модели и требуют экспертной проверки.

## Квота Gemini и повторный запуск

- Перед демонстрацией проверьте дневную и минутную квоты выбранной модели в Google AI Studio. Для запуска с чистой машины используйте проект с запасом квоты, при необходимости с подключённым биллингом. Квота общая для ключей одного проекта. [Лимиты Gemini API](https://ai.google.dev/gemini-api/docs/rate-limits)
- При короткой паузе CLI повторяет запрос в пределах бюджета ожидания. Если Gemini просит подождать часы, проверьте текущую квоту и повторите команду после восстановления доступа. Таймаут HTTP-запроса управляет временем ожидания ответа сервера.
- При исчерпании квоты рядом с отчётом сохраняется локальная контрольная точка `.<имя отчёта>.gemini-checkpoint.sqlite3`. Повторите ту же команду с тем же входным документом, моделью и путём к отчёту. CLI проверит сохранённые структурированные ответы и продолжит анализ. После записи отчёта или окончательной ошибки проверки ответа сохранённые ответы этого прогона удаляются. Файл контрольной точки исключён из Git, поскольку ответы могут содержать цитаты из документа. Флаг `--no-resume` запускает анализ без контрольной точки.
